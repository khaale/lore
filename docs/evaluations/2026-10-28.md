# Lore usage evaluation — 2026-10-28

These exploratory runs evaluated complete agent workflows, especially elapsed time
and token usage. They are observations, not a statistically established ranking
of tools, models or skill versions.

## Dependency discovery

The task was to identify the Java services in a subsystem, then enumerate the
observed Maven dependencies for a release, including versions, owning services,
sources and a top-ten summary. Lore agents used a supplied read profile and saved
index. The file agent used the source repository without Lore. Profile preparation
and index construction were excluded from agent measurements.

The prepared index contained 17,994 entities, including 17,114 package observations.
The expected result was 14 services, 461 coordinates and 780 coordinate/version
combinations. The latest three runs additionally exported and verified 2,508
unique coordinate/version/service associations against the original JSONL.

The current Luna median was 62.561 seconds and 35,938 uncached input plus output
tokens. The current Luna runs and Sol run each used nine model requests and eight
outer tool calls. All three passed exact verification of coordinates, versions,
owners and their associations.

The original four answers matched coordinate-level version and owner unions.
They contained no duplicate coordinates or versions. Their output format did not
retain the association between each owner and version, so that stronger property
cannot be verified from those answers alone. One version in the file-only answer
required URL decoding for comparison; the original answer was preserved.

The expanded skill led to more schema exploration, API lookups and projection
errors. The compact contract removed much of that overhead. Current trajectories
still varied: one Luna performed broad exploration and repeated observation
reads, producing one truncated tool output; the other used full collections and
local filtering without truncation. Sol used selective reference filters, but
still took longer overall and produced one truncated intermediate output.
Full saved answers, rather than truncated previews, were verified.

The latest prompts were reformulated and additionally requested the association
export. They used the same prepared index, but are not a strict A/B reproduction
of the historical prompts. The files-only agent was not rerun. The observed
improvement over earlier numbers cannot be attributed causally to skill edits.

## Controlled skill pilot

A separate pilot tested two frozen documentation variants across two synthetic
models with two independent Luna high repeats per cell: eight runs in total.
Runs were sequential in a predetermined mixed order, with fresh agent histories,
the same SDK and ready indexes, and no hints about expected answers.

The candidate replaced the first whole-workspace count example with a function
accepting a caller-selected `{type, where, select}` and clarified technical entity
metadata versus selected model properties. These changes were tested together.
The example did not directly demonstrate a concrete `where` object.

- Aggregation: 15 stations and 1,200 readings across several zones, seasons,
  analytes and revisions. Verification checked exact counts and sums for each
  station/revision group, rejected duplicates, and included distractor records.
- Reachability: 90 procedures and 160 reviews, with branching prerequisites,
  a cycle and unreachable records. Verification checked all 43 reachable
  procedures, 25 matching approved reviews and their source file.

All eight answers were exact, with no unsuccessful shell commands or truncated
outputs. The candidate did not produce a consistent improvement or a reliable
shift toward more selective reads. The predefined pilot acceptance threshold
was not met: at least 15% lower uncached input plus output on each task, with
no more than 10% elapsed-time regression and no correctness failures.

The first-example replacement was reverted. Only the accurate clarification of
`select` and technical entity metadata was retained; its effect was not measured
independently. No runtime API changes followed from this pilot.

## Query-level comparison

Two repeats per variant compared equivalent JS filtering and SDK `where`, with
identical selected fields and outputs, each opening a new workspace. OS disk
caches were not cleared. Measurements ran without concurrent evaluation agents.

| Corpus | Variant | Median query ms | Returned records | Serialized collection bytes | Median open + PTC ms |
| ------ | ------- | --------------: | ---------------: | --------------------------: | -------------------: |
| Small  | JS      |            1.32 |              132 |                      31,084 |                52.96 |
| Small  | where   |            1.28 |               43 |                      10,322 |                45.73 |
| Large  | JS      |           56.51 |           17,114 |                  12,323,739 |             1,755.83 |
| Large  | where   |           25.18 |            2,549 |                   1,864,963 |             1,876.39 |

`where` reduced materialized results substantially, but no whole-workflow speedup
was established. Query execution still scans the collection. Serialized size is
a result-footprint proxy, not measured heap allocation. Timed PTC calls include
the serialization probe: about 25 ms for the large JS variant and 4 ms for
`where`. Remaining call overhead includes boundary checks and response handling;
its components were not separately profiled.

Millisecond-level query differences do not explain the roughly minute-long
agent sessions. Further evaluation should focus on unnecessary model transitions,
repeated exploration and data printed into the model context, without prescribing
one domain-specific query path.

## Measurement limits

Session time runs from agent-session creation to the final assistant answer.
Usage comes from the last cumulative token event in each child session; parent
coordination is excluded. Cached input is already included in input and total.
Reasoning output is already included in output and is not added again.

Uncached input plus output is a descriptive token counter, not a monetary cost.
Cache hits and inference-service latency varied. In the first aggregation pair,
input/output were nearly identical while cached input differed by over 4,000
tokens, accounting for most of the apparent token regression.

One Sol run, two current Luna runs and two repeats per pilot cell are insufficient
for reliable model rankings or causal conclusions. The corpora, indexes, session
logs and full dependency exports remain local working artifacts; they are not
part of the published package. This report preserves the findings without
embedding external repository data or machine-specific paths.
